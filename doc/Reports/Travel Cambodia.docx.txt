1. Introduction
1.1 Purpose of the document
The purpose of this document is to describe the requirements for the Travel Cambodia system. It explains what the system should do and what it should not do. It also lists the main quality needs, such as usability, security, and performance.
This document is used to help the project team and stakeholders understand the same goals. It supports planning, design, development, and testing. It also helps the team check whether the final system meets the expected features and quality.
In short, this document is the main guide for building the Travel Cambodia prototype and improving it later.
1.2 Scope of the project
Travel Cambodia is a travel platform that helps local and international tourists find places to visit in Cambodia and plan their trips. The system focuses on providing clear travel information and simple trip planning.
The first version will be a mobile-friendly/website so users can access it easily on phones and computers. A mobile app can be considered later if needed.
The system will include these main features:
Place browsing and searching: Users can browse places by category and city, search by keyword, and view place details such as description, photos, contact info, and a map link.
Itinerary planning: Users can create a trip plan and organize places by days (Day 1, Day 2, etc.). Users can edit the plan and add simple notes.
User account (optional for MVP): If needed, users can register to save itineraries and view request history. For a simpler prototype, users can use the system without login and only provide phone/email when sending a request.
User ratings and comments: Users can give ratings on places and also comment in the place they have visited. They can also send pictures that they have visited in that area as well.
Admin Content management: Admin can add/edit/delete places, manage categories/cities.
Super Admin Panel: Super admin can create/delete admins & users, assign roles, manage permissions and reset passwords.
The project will be built step by step, starting with the MVP features first, then improving them for the Y2S2 prototype.
Not included in this version:
Real online payment integration
Full personalized AI recommendations
Large partner integrations or external booking APIs
1.3 Stakeholders involved
1.3.1 Travel Cambodia Project Owner/Management
The project owner (or project leader) guides the project direction. They provide requirements, review progress, and give feedback to make sure the system follows the project goals.
1.3.2 Content Admin/Operators
Admins manage the travel information inside the system. They add and update places, categories, and cities. They need access to the admin panel to do these tasks.
1.3.3 Tourists (Users)
Tourists are the main users. They use the system to search places, view place details, plan an itinerary and contact service providers. The system must be simple and easy for both local and foreign users.
1.3.4 Developers
Developers design, build, test, and deploy the system. They work with the project owner and admins to implement the requirements and ensure the system is stable and usable.
1.3.5 Tester 
Perform quality assurance (QA) to identify bugs and issues before the launch. They verify that all features work as described in the requirements and ensure the system is stable for users.
1.3.6 Designer
Responsible for the User Interface (UI) and User Experience (UX). They create the visual layout and flow of the application to ensure it is attractive, intuitive, and easy to navigate for tourists.
1.3.7 Project manager
Oversees the project timeline, resources, and tasks. They coordinate communication between the team and stakeholders to ensure the project stays on track and is delivered on time.
1.3.8 Super Admin
Create/Delete Admins & Users: Super Admins can add, edit, suspend, or remove any user or lower-level administrator across the entire instance.
Assign Roles: They define and assign administrative roles, determining who can manage specific, limited areas (e.g., help desk admins).
Manage Permissions: They control permissions, including the ability to restrict user access to sensitive information or specific applications.
Reset Passwords: They can reset passwords for anyone in the organization, including other administrators.
1.3.9 IT Support
Give support to customers on technical/non-technical problems.
1.4 Overview of the Travel Cambodia platform
The Travel Cambodia platform is an online system that helps tourists discover places in Cambodia and plan their trips. The main goal is to make travel planning easier by putting useful information in one place. Users can search for places, view details and build an itinerary.
The Travel Cambodia platform includes these main features:
1.4.1 Place Catalog
The place catalog contains a list of travel places, such as temples, beaches, food places, hotels, and activities. Each place includes simple information like name, description, photos, city, map link, and contact details. Users can browse by category and search by keyword.
1.4.2 User Accounts (Optional for MVP)
Users may create an account to save their itineraries and view their request history. If you want a simpler prototype, users can still use the platform without an account and only provide a phone number/email when sending a request.
1.4.3 Itinerary Planner
This feature helps users plan their trip day by day. Users can create a trip and add places to Day 1, Day 2, Day 3, and so on. Users can also edit the plan and add notes (example: time, meeting point, budget).
1.4.5 User ratings and comments: 
Users can give ratings on places and also comment on the place they have visited. They can also send pictures that they have visited in that area as well.
1.4.6 Admin Content Management
Admins manage the content in the system. They can add, edit, and delete places, manage categories and cities.
1.4.7 Super Admin Management
Super admin can create/edit/delete customers or admins accounts, assign roles, manage permissions and reset admin passwords.
This platform is designed to be easy to use, especially for tourists who need quick and clear travel information.

2.3 User characteristics
Travel Cambodia is an agency app created to help the client find their travel destination and help them organize their travel plan to maximize the efficiency, including: 
• Customers who are interested in browsing and planning the travel plans from Travel Cambodia. The users may have varying levels of budgets and interest to travel to different places inside Cambodia.
• The Travel Cambodia agency app is responsible for recommending, suggesting, and finding the perfect mapping, where the user checks out each place and what the user should do when they get there and customer support is provided. 
• The following are some of the key user characteristics that have been considered in the design of Travel Cambodia:
• Technical Proficiency: The app is designed to be as user-friendly as possible with relevant interactive UI and straightforward steps.
• Language: The app supports English/Khmer language only.
• Security: The app will require users to create user accounts and log in to access certain features, such as travel plan and user’s profile. The app will implement security measures to protect user data and prevent unauthorized access.
2.4 Constraints
The development of Travel Cambodia is a very important project to a wide range of local users for now. The development of the app includes:
• Technology Limitations: Currently, our reach on advanced technologies to recommend to the user with relevant interests is limited.
• Time Constraints: The development of the Travel Cambodia project has a tight deadline. This will require careful planning and execution to ensure the app is completed on time.
• Budget Constraints: The development of an app is subject to a fixed budget, which will need to be carefully managed throughout the development process.
• Legal and Regulatory Constraints: The app must comply with all relevant laws and regulations, including data protection and privacy regulations.
• Performance and Scalability Constraints: The portal must be designed to handle high levels of traffic and usage and must be scalable to accommodate future growth. But for now we still need time to scale it.
• Security reasons: The app needs some security measures to protect user data and prevent anomalous access.

2.6 Apportioning of requirements
The requirements for Travel Cambodia have been apportioned into different phases to enable a phased approach to development and deployment. The apportioning of requirements are based on the criticality and complexity of each requirement, as well as the dependencies between them.
The apportioning of requirements is as follows:
Phase 1: Basic our functionality
•	User registration and login
•	Browsing and search engine
Phase 2: Our advanced app functionality
•	Travel place recommendations
•	Customer reviews and ratings
•	Customer service
•	Social media integration
•	Relevant algorithm
Phase 3: Web application development
•	Design website UI for pc
•	Web-specific features, such as push notifications and location-based services
The apportioning of requirements enables a gradual and phased approach to development, allowing for incremental testing and validation of features. Each phase will be delivered based on a fixed timeline and budget, and the final product will incorporate all of the required features and functionality.

3.2 Non-functional Requirements
3.2.1 Performance requirements
+ Asset Loading
Requirement: The contents and images must occur within 1.5 seconds when the user is on the website. 
+ API
Requirement: The backend API must be able to handle at least 50 requests per second without crashing.

3.2.2 Security
+ Data Privacy & Authentication
Detailed Requirement: Passwords must never be stored in plain text. They must be very secure and can only be accessed by the data administrator.

3.2.3 Usability
+ Mobile Responsiveness & Layout
Requirement: The UI must adapt to other viewing methods like for mobile, tablet and computers
+ Error Feedback
Requirement: Error messages must be user-friendly in order for the user to know what’s going on instead of giving them technical terms.
3.2.4 Reliability & Availability
+ Recoverability
Requirement: The database must be saved and backed up automatically (every 24 hours). The system would be able to recover in 1 hour after any crashes.

3.2.5  Scalability
1. Database Scalability
Detailed Requirement: The database tables must be properly stored in the database (e.g., indexing the Place_ID column). This ensures that searching for reviews remains fast (under 1 second) even when the database grows larger.

4. Use Cases
4.1 Place browsing and searching use case
Diagram:

Product browsing and searching use case:
Description: This use case describes the process of browsing and searching for a travel destination or place on the Travel Cambodia platform.
Actors: 
Tourist (User): A local or international user who visits Travel Cambodia to find places to visit and plan their trip.
System: The Travel Cambodia platform that provides destination browsing, searching, and filtering functionality.
Preconditions: 
The tourist has internet access.
The tourist has opened the Travel Cambodia website (or app).
Post-conditions: 
The tourist can view a list of places matching their search criteria or category.
The tourist can view details of a specific place.
The tourist can add the place to their itinerary​Plan.
Basic Flow:
The tourist navigates to the search bar or the "Explore" section on the Travel Cambodia platform.
The tourist enters keywords (e.g., "Angkor Wat", "Cafe") or selects a specific Category (e.g., Temple, Beach) and City.
The system retrieves and displays a list of places matching the search criteria.
The tourist can filter the list of places by various parameters such as City, Category, or Rating.
The tourist clicks on a place to view its details (Description, Photos, Map link, Contact info).
The tourist selects "Add to Itinerary" to include the place in their trip plan (e.g., assigning it to Day 1).
Alternative Flows: 
If the tourist does not enter any keywords, the system displays a default list of places
If no places match the search criteria, the system displays a message informing the tourist that no places were found and suggests broader keywords.
If the tourist does not want to add the place to an itinerary immediately, they can simply navigate back to the list to browse other places.
Exceptions:
If the system is down or experiencing technical difficulties (e.g., database connection error), the tourist will be unable to load the place list. An error message will be displayed asking the user to try again later.
4.2 Itinerary Planner
Diagram:

Description: This use case describes the process of creating and organizing a travel plan (itinerary) on the Travel Cambodia platform.
Actors: 
Tourist: A user who wants to organize places into a trip plan.
System: The Travel Cambodia platform that provides the planning functionality.
Preconditions: 
The tourist has browsed and identified places they want to visit.
(Optional) The tourist is logged in to save the itinerary permanently.
Post-conditions: 
The itinerary is saved to the user's profile (or local storage for guest users). 
The system displays the organized trip schedule by day.
Basic Flow:
The tourist navigates to the "Itinerary Planner" section or clicks "Add to Plan" on a specific place.
The system prompts the tourist to create a new trip (entering trip name, start date, and end date).
The system creates a timeline (Day 1, Day 2, etc.).
The tourist assigns selected places to specific days and times.
The tourist adds simple notes (e.g., "Lunch here," "Bring camera") to the activities.
The tourist clicks "Save Plan."
The system confirms that the itinerary has been saved successfully.
Alternative Flows: 
If the tourist already has an existing trip, they can select it to add new places instead of creating a new one.
If the tourist wants to remove a place, they can delete it from the specific day.
Exceptions:
 If the tourist is not logged in and tries to access the plan from a different device, the data will not be available (if stored locally). The system prompts the user to register to sync data.
4.3 User account management use case
Diagram:

Description: This use case describes how a Tourist/Traveller registers an account via OTP verification, logs in, and manages their profile settings.
Actors:
Tourist/Traveller: A user who wants to create and manage an account (Primary).
System: The Travel Cambodia platform.
Google: An external identity provider used for registration and login (Secondary).
Preconditions:
The Tourist/Traveller has internet access.
Post-conditions:
The Tourist/Traveller has a verified account.
The Tourist/Traveller is logged into the system.
Profile changes, such as name or picture updates, are saved.
Basic Flow:
The Tourist/Traveller selects User Register and chooses a method: Google, Email, or Phone number.
The System triggers the Send OTP process to verify the user's identity.
Once verified, the Tourist/Traveller proceeds to Log in using their credentials or Google authentication.
The Tourist/Traveller accesses Profile Management to view their account details.
The Tourist/Traveller selects Change Profile Picture / Name to update their information.
Alternative / Extended Flows:
Forgot Password: From the Log in screen, the Tourist/Traveller can select Forgot Password, which triggers Reset Password and a mandatory Send OTP verification to the user's Google/Email.
Log out: From the Profile Picture / Name change screen, the Tourist/Traveller can choose to Log out of the system.
Delete Account: From the Profile Picture / Name change screen, the Tourist/Traveller can choose to permanently Delete Account.

5.Appendices
5.1 Glossary of Terms (Travel‑Centric)

Admin (Content Admin): A system operator who manages travel information inside the platform, including adding and updating places, categories, and cities.
Itinerary: A planned trip schedule that allows users to organize places to visit by specific days (e.g., Day 1, Day 2) and add personal notes.
One-Time Password (OTP): A temporary code sent to a user's email or phone, used for secure registration, login verification, and resetting forgotten passwords.
Super Admin: A top-level administrator who has the authority to create, edit, or delete customer and admin accounts, assign roles, manage permissions, and reset passwords across the platform.
Tourist: The primary user of the platform (either local or international) who uses the system to discover destinations, read reviews, and build travel plans.
